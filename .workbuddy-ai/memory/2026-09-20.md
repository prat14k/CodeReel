# 2026-09-20

## Settings buttons reported as "Something went wrong" (oMLX)

Investigated a report that Load models / Test connection / Find local servers all
failed even with a correct API key.

### What was proven working
Drove the three calls through the app's own `Engine` + `API` with `VOXDEMO_PROBE=1`
(added to `Snapshots.runIfRequested()`), so the real code path is exercised and the
real error string is printed instead of being buried in a modal:

- `/providers/models` → ok, 9 models
- `/providers/test`   → ok, 461 ms, reply `{"ok":true}`
- `/providers/detect` → 2 servers

Also ruled out, in order: server endpoints (all 200 via curl), Swift URL
construction (`base.appending(path:)`), a standalone Swift client, a matrix of
provider configs, and event-loop starvation — the `/providers/*` handlers are sync
`def`, so FastAPI runs them on the threadpool, not the loop.

### The actual defect
`API.send()` flattened *every* transport failure into `APIError.offline`:

```swift
catch { throw APIError.offline }   // "The engine isn't answering on 127.0.0.1:8809."
```

A timeout is not an unreachable engine. When oMLX is cold (still loading weights)
or the machine is busy loading VoxCPM's own 5 GB model, the request times out and
the user is told to go restart the engine — for a problem that is upstream of it.
The modal title is a bare "Something went wrong", so there was no way to tell which
of ~15 call sites failed.

### Changes
- `VoxDemoApp.swift`: added `APIError.timedOut(TimeInterval, String)`; `send()`
  now checks `ns.domain == NSURLErrorDomain && ns.code == NSURLErrorTimedOut`
  (verified = -1001 against a deliberately slow local server) and reports the
  endpoint and the timeout. Verified classification with a 5 s-sleep server and a
  1 s `timeoutInterval`.
- `SettingsView.swift`: `loadModels()` no longer pushes routine failures into the
  global `engine.lastError` modal. It sets a new `@State modelError` rendered
  inline under the buttons, suffixed by `sentWith()` — "Sent to <base_url> with
  the key typed in the field / the stored key / no key at all". That answers
  "I did set the key correctly" directly.
- `providers.py`: `list_models` default timeout 8 → 15 s. A server still loading
  weights accepts the socket then stalls; the Swift side already allows 60 s.

### Also gated the buttons on the engine
`SettingsView` ran Load models / Test connection / Find local servers unconditionally.
They now carry `|| engine.health == nil`, with a "Waiting for the engine — these need
it running." caption. Rationale: every one of them needs the sidecar, and firing before
it answers is a connection-refused that reads as "your API key is wrong".

### Hypotheses ruled out (with measurements)
- **Timeouts.** Python always returns first — `list_models` 15 s vs Swift 60 s; `test`
  ~135 s vs 240 s; `probe_local` 20 s vs 180 s. So `APIError.timedOut` is nearly
  unreachable from these three endpoints; the fix is correct but is not the symptom.
- **Memory pressure.** 48 GB total, 91 % free, 1.6 GB swap used. Not the cause.
- **Slow model load.** In a 180 s soak the provider calls returned `ok=true` at t=10 s
  and t=20 s *while* `loading=true`. A busy engine does not block Settings.
- **Early tap.** Port listening at 593 ms, `/health` at 626 ms after launch. Too fast
  to catch by hand.
- **Orphaned sidecar.** Soak held sidecar pid 96007 for the full 180 s, 18/18
  `/providers/models` ok, `ready=true` from t=30 s, port freed on quit. The lifecycle
  fix from 2026-09-18 holds.

Conclusion: the reported failure came from the pre-fix state (a stranger sidecar
answering /health while 404ing `/providers/*`), which cannot recur now that the child
dies with the parent and the app vacates occupied ports. What remained broken was the
*reporting*, now fixed.

### Regression test added
`contract_check.py` now enforces the cross-language invariant this bug hid behind:
**python's internal budgets must stay under the swift client's deadline**, or the client
gives up first and the user is told the engine is unresponsive when the real problem is
upstream. Budgets are read out of `providers` (`inspect.signature` for the defaults,
regex over `inspect.getsource(providers.test)` for its two literals), so raising a real
timeout updates the check rather than silently drifting past it.

```
[OK ] /providers/models python 15s < swift 60s
[OK ] /providers/test python 135s < swift 240s
[OK ] /providers/detect python 20.0s < swift 180s
```

Proved it bites: temporarily set `list_models` default to 90 and the check failed with
"python budget 90s is not under the swift client budget 60s", then reverted (verified by
grep, not by trusting the edit).

Also aligned `providers.test()`'s own `list_models(p, timeout=8)` to 15 — otherwise
"Test connection" could fail its model listing at 8 s while "Load models" succeeded at
15 s, which is its own kind of confusing.

### State after
Engine reaches `ready=true`. `swift build -c release` clean; `contract_check.py` all OK;
no orphan sidecars left on 8809.

### Closed the last loose ends
The first round only moved `loadModels()` off the global modal — `runTest()` and
`detect()` still pushed throws into `engine.lastError`. The user's report covered all
three buttons, so the fix was incomplete. Now all three share a single
`@State providerError` shown next to the buttons, cleared on entry to any of the three
and on a preset change. `modelError` was renamed to `providerError` to match what it
actually holds.

Also added a `shell-settings-no-engine` snapshot variant in `Snapshots.swift` that
overrides `engine.health = nil`, so the caption and the disabled buttons can actually be
seen. Verified the three buttons render grayed-out and "Waiting for the engine — these
need it running." appears beneath them when the engine is down.

### LibraryView: failed refresh used to look like a deleted library
`LibraryView.refresh()` silently set `demos = []` on a failed `/library` — which reads
exactly like "you deleted everything". Added a `@State loadError` and an inline error
card with a Retry button. The offscreen snapshotter can't exercise this branch (the
`.task` doesn't complete in time during capture), so verification rests on the build +
the parallel pattern with Settings. The `remove()` failure still goes through the
global modal — showing it inline per-row would be a much bigger change for a transient
destructive action where the row disappears on success anyway.

### VoicesView: save failures get inline too
`VoicesView.save()` (clone a voice) now writes to a `@State saveError` and renders the
message inline next to the save button — same place `recorder.problem` already lives,
so the pattern matches. `preview()` and `remove()` still hit the global modal: preview
produces no obvious on-screen artefact to attach an error to, and remove is a per-row
destructive action where inline state is heavier than the modal is unhelpful.

`VoicesView.preview()` later got the same treatment — it was the worst offender of the
lot: on failure nothing appears at all (no audio bar, no message), so you press Preview
and get silence with no explanation. Now a `@State previewError` renders in the preview
card under the "Waiting for the engine" notice.

### CreateView: `SourceStep.detect()` inline
Same treatment — `@State detectError` rendered under the Detect button. `analyse()`,
`preview()` and `generate()` deliberately still use the global modal: they are
step-blocking flows (the whole wizard is waiting on them, with `busy` and progress
already on screen), so a modal that stops you is the right shape there, not an inline
caption.

### Where the pattern stops
Rule of thumb settled on: **inline when the failure is local to one control and the
screen is still usable; modal when the flow is blocked.** Applied to Settings (all
three provider controls), Library refresh, Voices save **and preview**, Create detect.
Left on the modal: Library remove, Voices remove, Create analyse/preview/generate —
the last three are step-blocking flows where `busy` and progress are already on screen
and stopping you is the right shape.

One more confirmation of a round-1 finding: this final probe caught the engine at
`loading=true` again, and `/providers/models` and `/providers/test` both still returned
`ok=true`. A loading engine does **not** block the provider controls.

### What the error text actually says (verified, not assumed)
Drove `/providers/models` at four providers to see the string the user would land in
the inline error:

| case | ok | error |
|---|---|---|
| dead port 9999 | False | `HTTP 502 … upstream connect failed` (proxy artefact, see below) |
| wrong port 8001 | False | same proxy artefact |
| oMLX + bogus key | False | `401 from http://127.0.0.1:8000/v1/models — the API key was rejected.` |
| oMLX + no key | **True** | — (falls back to the stored key) |

The 401 message is genuinely good, and with `sentWith()` appended the user gets the
HTTP status, the URL, the reason, and which key was sent. The last row confirms
`Provider.resolved()` really does fall back to the stored key when the draft's
`api_key` is empty — worth knowing, because it means "no key" is not a failure mode.

The 502s are a sandbox artefact: the shell sets `http_proxy`, and the sidecar's own
`urllib` in `providers.py` honours it, so a refused connection is reported by the
proxy rather than as a connect error. On a normal machine that case says
`could not reach …`. Recorded in MEMORY.md.

### Locked down: unreachable host must surface a non-empty error
Added to `contract_check.py`: a provider pointing at `127.0.0.1:9999` must come back
with `ok=false` AND a non-empty `error` field. That string is what renders in the
Settings inline error UI — if it ever goes empty, the user gets the generic modal
with no information. Passing now (`105 chars`). Proved the test runs by grepping
the harness output rather than relying on `tail -N`.

### Bug caught in my own change: detect() must not claim what was sent
Reviewing the diff before closing, `SettingsView.detect()` was appending `sentWith()`
like the other two handlers. But `/providers/detect` scans `COMMON_PORTS` — it never
uses the form's `base_url` or `api_key`. So a failure there would have told the user
"Sent to http://127.0.0.1:8000/v1 with the stored key", which is simply false, and
would have sent them to fix a URL that was never involved. Fixed: `detect()` now uses
the bare `error.localizedDescription`, with a comment saying why it differs from its
two neighbours. `sentWith()` remains correct in `loadModels()` and `runTest()`, both of
which really do send the form's config.

**Lesson:** a diagnostic helper that is right in two of three call sites is still wrong
in the third. The whole value of `sentWith()` is that it is trustworthy; one misuse
poisons it.

### Second self-review bug: snapshot shot was mutating the shared sample engine
My `shell-settings-no-engine` variant in `Snapshots.swift` did
`var deadEngine = engine; deadEngine.health = nil`. `Engine` is a class, so this
copied the reference, and `deadEngine.health = nil` mutated the *shared* sample
instance. Every shot after that one — the create-flow steps, `control-list`,
`sheet-welcome` — rendered with `health == nil` because they reused the same
`engine` variable. The dead-engine shot looked correct in isolation, and every
earlier snapshot of `shell-settings` (taken before my insertion) was correct, so
the regression slipped through both rounds of verification. Fixed by calling
`sampleEngine()` a second time so the dead-engine shot has its own instance.
Verified by re-running `VOXDEMO_SNAPSHOT` and reading `step-0.png` (now `Engine
ready`, previously would have been `Engine stopped`).

**Lesson:** reference types in test fixtures. `let a = b` is *not* a snapshot.
This is the "it works in isolation" variant of the bug — every shot looked fine
on its own, the side effect only shows up in the next one.

### Third self-review bug: buttons enabled before the form is initialised
The gate was `engine.health == nil`, but `Engine.watch()` assigns `health` and only
*then* calls `loadSettings()`. Between the two, the buttons are live while
`SettingsView.draft` is still the default `ProviderConfig()` — whose `kind` is
`"openai"` (so the buttons do render) and whose `base_url` is `""` (so the request
goes nowhere). A Load models tap in that window reports `Sent to  with no key at
all`. Introduced `formReady` (`engine.health != nil && engine.settings != nil`) and
switched all four uses — three `.disabled(...)` and the caption — to `!formReady`.

Three bugs in three passes, all the same shape: **correct in isolation, wrong
because of a state the proximate check didn't cover.** Each one was invisible to
the test that looked at it directly.

### The modal title now categorises
`RootView.alertTitle` derives the title from the error text instead of always saying
"Something went wrong": mentions of `api key` / ` 401` / `provider` / `/v1/` become
**"Provider problem"**; `engine` / `model` / `weights` / `127.0.0.1` become
**"Engine problem"**; anything else falls back to the old generic title. This is
keyword matching and I'd normally avoid it, but the modal is fed by ~12 call sites
that all write a bare `String`, and threading a structured error through all of them
is a much bigger change for a UI title. Worst case it degrades to the current
behaviour. Probe green afterwards; the alert itself can't be captured offscreen
(alerts are separate windows), so this one rests on the build and code review.

### Seed-and-revert: how to see UI that only appears on failure
Library's error card, Voices' saveError/previewError, and Create's detectError all
render *only* when their `@State` error string is non-empty, which never happens in a
clean snapshot. Technique used here: temporarily seed the `@State` to a sample
error string, render with `VOXDEMO_SNAPSHOT`, read the PNG, then revert and rebuild.
Three views verified in one build cycle. Critical: verify the revert *with the
Grep tool*, not bash `grep` — BSD grep's `\|` silently matches nothing and I almost
read an empty grep result as a missed revert (caught because the build still
succeeded).
